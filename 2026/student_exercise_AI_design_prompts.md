# 學生練習：請 AI 幫你設計追番系統

## 使用方式
把下面其中一個 prompt **完整複製**貼給 Claude / ChatGPT / Gemini，  
收到答案之後，用今天學到的 Database Thinking **驗證 AI 的設計**。

---

## Level 1｜基本款（第一次用 AI 設計系統）

```
我想做一個追番清單 App，功能很簡單：
- 使用者可以註冊、登入
- 可以新增動漫到自己的追番清單
- 可以記錄每部動漫的觀看狀態（想看、看中、看完）
- 可以給每部動漫評分（1 到 5 顆星）

請幫我：
1. 設計 MongoDB 的 Collection 結構，列出每個 Collection 的欄位
2. 說明哪些地方用 Embedding，哪些地方用 Referencing，並解釋原因
3. 設計 3 個最重要的 REST API endpoint，包含 HTTP method 和路徑

請用繁體中文回答。
```

### Level 1 收到答案之後：驗證清單

**Step 1：檢查基本結構**

| 驗證問題 | 你的判斷 |
|---------|---------|
| 每個 Collection 都有 `_id` 嗎？ | |
| 有沒有 `createdAt` 欄位？ | |
| `email` 有沒有標注唯一（unique）？ | |
| 密碼是存明文還是 hash？ | |
| API 命名有沒有用動詞？（不應該有） | |

**Step 2：追問 AI 這些問題**

```
針對你剛才的設計，我想多了解：

1. 你把評分放在 watchlist 裡，而不是獨立一個 Collection，
   這樣設計的好處和壞處是什麼？
   如果未來要做「全站平均評分排行榜」，這個設計夠用嗎？

2. 這份設計裡你最不確定的地方是哪裡？
   有沒有什麼欄位你猜我可能需要，但你不確定？
```

**Step 3：反思問題（寫下你的答案）**

- AI 的 Embedding / Referencing 選擇，跟你自己想的一樣嗎？哪裡不同？
- 如果使用者想「只看完結的動漫」，這個 Schema 查得到嗎？怎麼查？
- 你覺得 AI 漏掉了什麼？

## Level 2｜進階款（想挑戰更多細節）

```
我要開發一個多人追番清單平台，類似 MyAnimeList，需求如下：

使用者功能：
- 註冊／登入（email + 密碼）
- 個人資料頁（頭像、自我介紹）
- 可以追蹤其他使用者

動漫功能：
- 動漫資料庫（片名、類型、集數、狀態：連載中／完結）
- 每部動漫有多個分類標籤（例如：戰鬥、愛情、異世界）

追番功能：
- 每個使用者有自己的追番清單
- 記錄：觀看狀態、看到第幾集、個人評分、個人筆記
- 可以設定公開或私人

請幫我：
1. 設計完整的 MongoDB Schema，每個 Collection 列出所有欄位與資料型別
2. 標出哪些欄位應該建立 Index，並說明原因
3. 列出 Embedding 和 Referencing 的決策，並解釋每個選擇的取捨
4. 設計 RESTful API 路由表（至少 6 個 endpoint）
5. 指出這個設計在用戶量大時可能遇到的效能問題

請用繁體中文回答，並用表格呈現 Schema。
```

### Level 2 收到答案之後：驗證清單

**Step 1：檢查設計決策**

| 驗證問題 | 你的判斷 |
|---------|---------|
| genres 標籤是 Embed 還是 Reference？理由合理嗎？ | |
| follows（追蹤關係）怎麼設計？能查「我追蹤誰」和「誰追蹤我」嗎？ | |
| Index 有沒有涵蓋最常查的欄位？ | |
| watchlist 能同時支援「公開」和「私人」查詢嗎？ | |
| API 路由有沒有版本號（`/v1/`）？ | |

**Step 2：追問 AI 這些問題**

```
針對你剛才的設計，請回答：

1. follows 這個關係你怎麼設計的？
   如果我要查「A 追蹤的人最近加了什麼番」，
   這個查詢要跨幾個 Collection？效能上有什麼問題？

2. genres 標籤你選擇 Embed，
   如果未來標籤要支援多語言（中文、日文、英文），
   現在這個設計要怎麼改？改動大不大？

3. 這份設計裡，你覺得哪個決定最有爭議？
   如果換一個工程師來看，最可能不同意你哪個地方？
```

**Step 3：反思問題（寫下你的答案）**

- AI 說的效能問題，你覺得哪一個最嚴重？為什麼？
- 「公開 / 私人清單」這個需求，AI 的設計方式是什麼？你認同嗎？
- 如果你是 reviewer，你會要求 AI 改哪一個地方？

## Level 3｜地獄款（想看 AI 的極限在哪）

```
我要設計一個追番社群平台的後端系統，技術需求如下：

產品需求：
- 多用戶系統，預計初期 1 萬名用戶，未來擴展到 100 萬
- 使用者可建立追番清單，記錄觀看進度
- 動漫可以有季度（Season）和集數（Episode）層級的追蹤
- 社群功能：評論、按讚、追蹤其他用戶
- 推薦系統需要記錄用戶的觀看歷史和評分行為

技術限制：
- 使用 MongoDB + Flask + Python
- 需要考慮效能：熱門動漫的讀取要快
- 需要考慮資料一致性：評分更新時要同步

請提供：
1. 完整 MongoDB Schema 設計（所有 Collection、欄位、型別）
2. 每個 Collection 的 Index 策略
3. Embedding vs Referencing 的完整決策文件
4. RESTful API 設計（完整路由表，含 Request / Response 格式）
5. 當用戶量從 1 萬成長到 100 萬時，哪些地方會先爆掉？要怎麼處理？
6. 有哪些地方你這樣設計，但實際上可能需要根據業務需求調整？

請用繁體中文，結構化呈現所有內容。
```

### Level 3 收到答案之後：驗證清單

**Step 1：挑戰 AI 的每個決策**

| 驗證問題 | 你的判斷 |
|---------|---------|
| seasons / episodes 是 Embed 的，如果集數破千（海賊王）document 會多大？ | |
| avg_rating 是冗餘欄位，100 萬人同時評分時怎麼保證資料一致？ | |
| watch_history 沒有做分頁或 TTL，資料會無限成長嗎？ | |
| 推薦系統的資料收集設計，真的夠用嗎？ | |
| 有沒有軟刪除（soft delete）設計？刪掉的資料還能查嗎？ | |

**Step 2：追問 AI 這些問題**

```
針對你剛才的設計，我要挑戰幾個決策：

1. seasons 和 episodes 你選擇 Embed 在 anime document 裡，
   《海賊王》有 1000 集以上，這個 document 會有多大（估算 KB）？
   MongoDB 單一 document 上限是 16MB，這個設計安全嗎？
   什麼情況下你會改成 Referencing？

2. avg_rating 你用冗餘欄位，
   如果 100 萬用戶同時在評分《鬼滅之刃》，
   這個欄位的更新會有 race condition 嗎？
   你會怎麼解決？

3. 這整份設計裡，你最沒把握的地方是哪裡？
   有哪些假設你做了，但你不確定是否符合我的需求？
   如果我只告訴你一件額外的需求，最有可能讓你大改設計的是什麼？
```

**Step 3：反思問題（寫下你的答案）**

- AI 承認「最沒把握」的地方是什麼？你同意它的自我評估嗎？
- 比較 AI 第一次的答案和追問之後的答案，它改變了什麼？為什麼？
- 如果你要把這份設計交給真正的開發團隊，你還需要補充哪些資訊？
- AI 給的答案裡，有沒有讓你「感覺說得很對但其實不確定」的地方？那個感覺很重要——那就是你需要自己去查的地方。

## 所有 Level 共用：最後一個追問

不管選哪個 Level，最後都貼這句話給 AI：

```
你剛才的設計，有沒有哪些地方是你「假設」了某個需求，
但我其實沒有明確說？
把你做的假設全部列出來。
```

> 這個問題的答案，就是你作為工程師需要跟 stakeholder 確認的清單。
> AI 說得出來的假設，代表它知道自己在猜。
> AI 說不出來的假設，才是真正的風險。
